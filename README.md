# AlphaCRM — CRM амбулаторной клиники

Внутренняя система клиники: вход сотрудников по логину и паролю, расписание нескольких врачей по дням и неделям, регистратура (задачи и лист ожидания), карточки пациентов, приём и подписание медицинских документов, касса, аналитика посещаемости и журнал аудита. Frontend на React/MUI, backend на Spring Boot с модульной архитектурой, база PostgreSQL. Все seed-данные синтетические. Проект не заявляет соответствие законодательству или регуляторным требованиям.

Сотрудник видит продукт как **AlphaCRM**. Внутренние имена прежние — пакет `ru.quietclinic`, Maven-координаты, имя Compose-проекта, база и пользователь `quiet_clinic`: от них зависит уже созданная база и её том, поэтому они не переименовываются.

Подробная документация: [архитектура проекта](docs/architecture.md) и [хранение данных — схема базы](docs/data-model.md).

## Быстрый старт

Нужен только [Docker Desktop](https://www.docker.com/products/docker-desktop/). Java, Maven и Node.js для запуска ставить не нужно: всё собирается внутри контейнеров.

Из корня проекта:

```powershell
.\scripts\start.ps1        # Windows PowerShell
```

```bash
./scripts/start.sh         # WSL, Linux, macOS
```

Откройте **http://localhost:8080** и войдите (см. [Вход сотрудников](#вход-сотрудников)). Первая сборка занимает несколько минут, следующие запуски — секунды.

Что делает скрипт:

1. При первом запуске создаёт `.env` со случайным паролем БД, ключом шифрования и паролем начального администратора и печатает этот пароль (`scripts/init-env.sh` или то же внутри `start.ps1`). В существующем `.env` ничего не меняет, только дописывает `CLINIC_ADMIN_PASSWORD`, если его там ещё нет (`.env` от прошлой версии; прежний `CLINIC_BOOTSTRAP_PASSWORD` удаляется).
2. Если `.env` новый, а в Docker уже есть база от прошлых запусков, останавливается и объясняет, что делать (иначе пароли не совпадут).
3. Собирает образы и запускает `docker compose up -d --build --wait`: команда завершается, только когда все сервисы прошли healthcheck.
4. При ошибке сам показывает состояние контейнеров и последние строки лога backend.

> **Сохраните копию `.env` в надёжном месте.** В нём ключ шифрования клинических текстов: без него зашифрованные данные в базе прочитать нельзя.

## Что запускается

`compose.yaml` поднимает три сервиса:

| Сервис | Что внутри | Доступ |
|---|---|---|
| `frontend` | nginx без root: статика интерфейса, прокси `/api` → backend, gzip, кэш для файлов сборки, CSP и security headers | `http://127.0.0.1:8080` |
| `backend` | Spring Boot на JRE 21 без root, профиль `prod` | только из nginx, наружу не публикуется |
| `postgres` | PostgreSQL 18, данные в томе `quiet-clinic_quiet-clinic-postgres` | `127.0.0.1:55432` — для IDE и утилит |

Интерфейс и API работают на одном адресе, поэтому CORS не нужен. Все сервисы перезапускаются автоматически (`restart: unless-stopped`) и стартуют по порядку: база → backend → frontend.

Профиль `prod` (`application-prod.yml`):

- graceful shutdown: при остановке текущие запросы дорабатывают до 20 секунд;
- Swagger UI и `/v3/api-docs` выключены, детали health скрыты;
- корректная работа за прокси (`X-Forwarded-*`);
- приложение **не стартует**, если ключ шифрования не задан, короче 32 символов или похож на значение по умолчанию;
- приложение **не стартует** без `CLINIC_ADMIN_PASSWORD`, если он короче 12 символов или равен `admin`;
- начальный администратор обязан сменить пароль при первом входе, до остальных страниц.

## Управление

```bash
docker compose ps                    # состояние и health сервисов
docker compose logs -f backend       # логи backend (frontend, postgres — аналогично)
docker compose up -d --build         # пересобрать и перезапустить после изменений кода
docker compose restart backend       # перезапустить один сервис
docker compose down                  # остановить; данные сохраняются
docker compose down -v               # остановить и УДАЛИТЬ базу со всеми данными
```

В WSL остановка также: `./scripts/stop.sh`.

### Резервная копия базы

Команды работают одинаково в PowerShell и bash. Пользователь и база — из `.env`, по умолчанию `quiet_clinic`.

```bash
# создать копию
docker compose exec postgres pg_dump -U quiet_clinic -Fc -f /tmp/backup.dump quiet_clinic
docker compose cp postgres:/tmp/backup.dump ./backup.dump

# восстановить из копии
docker compose cp ./backup.dump postgres:/tmp/backup.dump
docker compose exec postgres pg_restore -U quiet_clinic -d quiet_clinic --clean --if-exists /tmp/backup.dump
```

Вместе с копией базы храните `.env` с тем же `CLINIC_KMS_KEY`.

## Вход сотрудников

Учётные записи хранятся в базе (`staff_user`): клиника, ФИО, логин, bcrypt-хеш пароля, роль, карточка врача (только у врача), признак «активен» и «сменить пароль при входе». Внешний OIDC/Keycloak не используется. Зашитых сотрудников нет: ни паролей, ни хешей в коде и миграциях.

**Первый запуск.** Если в базе нет ни одного сотрудника, приложение создаёт клинику (название из `CLINIC_NAME`) и её **владельца** (`OWNER`) с логином **`admin`** и паролем из `CLINIC_ADMIN_PASSWORD`; хеш считается при старте bcrypt со своей солью. На уже работающей базе миграция `quietclinic:029` делает владельцем начальную учётную запись `admin`, если владельца в клинике ещё нет: только владелец назначает старших администраторов и владельцев.

| Профиль | Вход | Смена пароля |
|---|---|---|
| `local` (H2, разработка) | **`admin` / `admin`** (`application-local.yml`) | не требуется |
| `prod` (Docker) | `admin` / пароль из `CLINIC_ADMIN_PASSWORD` в `.env` | обязательна при первом входе |

Дальше людей заводит администратор в разделе «Сотрудники»: имя, логин, роль, временный пароль, который он вводит сам. Пароль показывается один раз, в базе лежит только хеш. При первом входе сотрудник обязан задать свой пароль — до этого API отвечает `403 PASSWORD_CHANGE_REQUIRED` на всё, кроме `/auth/me`, `/auth/password`, `/auth/logout`. Врач связывается с карточкой врача своей клиники.

Демо-врачи (Петров, Лебедева) и демо-пациенты остаются в расписании локальной базы, но учётных записей у них нет: войти под ними нельзя, пока администратор сам не заведёт сотрудника и не свяжет его с карточкой врача. Учётные записи прежних демо-логинов (`smirnova`, `petrov` и др.) удаляет миграция `quietclinic:016`. Старый changeset `quietclinic:013` не переписывается (Liquibase сверяет контрольные суммы), поэтому прежний хеш остаётся в его тексте, но в базе после 016 его нет.

**Несколько клиник.** У `staff_user`, `practitioner` и `patient` есть `clinic_id`, сессия знает клинику сотрудника, и пациенты, врачи, записи, сотрудники, задачи, счета, журнал и архив документов ограничены ею. Вторая клиника добавляется строкой в `clinic` и своим администратором в `staff_user` (логин уникален во всей установке) — без правки кода. Общего списка сотрудников на все клиники и экрана выбора клиники нет.

Как устроено:

- `POST /api/v1/auth/login {username, password}` открывает сессию: cookie `JSESSIONID` с `HttpOnly` и `SameSite=Lax`, срок 8 часов. Неверный логин и неверный пароль дают одинаковый `401 INVALID_CREDENTIALS`; отключённый сотрудник войти не может; пароль в лог не пишется. После 5 неудач подряд на один логин с одного адреса (или 20 с адреса вообще) вход с этого адреса закрыт на 15 минут — `429 TOO_MANY_LOGIN_ATTEMPTS`. Счётчики в памяти backend; настройки `clinic.login.*`.
- `GET /api/v1/auth/me` — текущий сотрудник (без хеша), `POST /api/v1/auth/logout` — выход, `POST /api/v1/auth/password {currentPassword, newPassword}` — смена своего пароля (нужен текущий, новый — от 8 символов).
- Роль и автор действия сервер берёт из сессии. Для врача автор (`actorId`) — id его карточки врача, поэтому записи журнала аудита и связь с лечением остались прежними. Заголовки `X-Demo-Role` / `X-Actor-Id` больше ничего не решают.
- CSRF включён: сервер кладёт токен в cookie `XSRF-TOKEN`, интерфейс отправляет его заголовком `X-XSRF-TOKEN` на изменяющих запросах. Все запросы идут с `credentials: 'include'`. Интерфейс и API работают на одном origin (nginx в Docker, прокси Vite при разработке); CORS для локальной разработки разрешает cookie только с явных адресов из `CLINIC_CORS_ORIGINS`, не `*`.
- Без входа видна только страница входа; `401` от API возвращает на неё. Если сервер недоступен, на странице входа можно открыть **песочницу** с одной из ролей («Песочница: Врач» и т. п.): без людей и логинов, помечена в шапке, работает на встроенных данных в памяти вкладки и ничего не отправляет на сервер.
- Раздел «Сотрудники» (администраторы и менеджер своей клиники; техподдержка — список и сброс пароля): создать сотрудника с временным паролем, отключить или включить, задать новый временный пароль — только для ролей не выше своих (`403 ROLE_NOT_ASSIGNABLE`). Себя отключить нельзя; врачу нужна существующая карточка врача этой клиники, остальным ролям — никакой; хеши паролей наружу не отдаются.
- **Несколько ролей** (кнопка «Роли»): `PUT /api/v1/staff/{id}/roles {roles: [...]}` — права ролей складываются и действуют сразу, без нового входа. Менять можно только роли не выше своих — и снимаемые, и добавляемые (`403 ROLE_NOT_ASSIGNABLE`); свои роли — нельзя (`409 CANNOT_CHANGE_OWN_ROLES`); роль врача связана с карточкой врача и здесь не добавляется и не снимается (`409 DOCTOR_ROLE_FIXED`). `role` — основная роль (у врача — `DOCTOR`), `roles` — все. `GET /auth/me` отдаёт `roles` и `permissions` — объединение разрешений всех ролей.
- **Ставки и условия работы** (`hr`): `GET /api/v1/hr/contracts/me` — свои условия, каждому сотруднику; `GET /api/v1/hr/contracts` (действующие у всех), `GET/PUT /api/v1/hr/contracts/{staffId}` — только владелец. Новые условия `{position, rateMinor, rateUnit, validFrom}` (`rateUnit` — `MONTH`, `HOUR`, `VISIT`) закрывают прежние днём раньше (`409 CONTRACT_DATE_TOO_EARLY`, если начинаются не позже них). В журнал — факт чтения и изменения, без сумм и должностей.

Вход из командной строки:

```bash
# токен CSRF и cookie сессии сохраняются в cookies.txt
curl -c cookies.txt -b cookies.txt -s http://localhost:8080/api/v1/auth/csrf
TOKEN=$(grep XSRF-TOKEN cookies.txt | awk '{print $7}')
curl -c cookies.txt -b cookies.txt -H "X-XSRF-TOKEN: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<CLINIC_ADMIN_PASSWORD>"}' http://localhost:8080/api/v1/auth/login
curl -b cookies.txt 'http://localhost:8080/api/v1/patients'
```

При разработке (`local`) — `admin` / `admin` и адрес `http://127.0.0.1:8081`.

## Перед выходом в сеть

Текущая сборка готова к запуску на одном компьютере. Прежде чем открывать её другим людям (`APP_BIND=0.0.0.0` или сервер в интернете):

- **Пароли.** Сразу после первого входа задайте каждому сотруднику личный пароль в разделе «Сотрудники» (или попросите сменить свой через «Сменить пароль»): начальный пароль из `.env` общий для всех.
- **HTTPS.** Поставьте перед `frontend` reverse proxy с сертификатом (Caddy, Traefik или nginx) и включите `SESSION_COOKIE_SECURE=true`. Для Caddy (`/etc/caddy/Caddyfile`), со скрытием заголовка `Server`:

  ```
  crm.example.ru {
      header -Server
      reverse_proxy 127.0.0.1:8080 {
          header_down -Server
      }
  }
  ```
- **Часовой пояс.** Задайте `CLINIC_TIME_ZONE` (например `Europe/Moscow`) до того, как вносить настоящие записи.
- **Ключи.** Храните `CLINIC_KMS_KEY` в менеджере секретов; dev-адаптер `KmsPort` замените на KMS-провайдера.
- **Резервные копии** по расписанию (см. [Резервная копия базы](#резервная-копия-базы)).

## Разработка

Для разработки с hot reload нужны **JDK 21 или новее** (проект компилируется под Java 21; JDK 23 из IDEA тоже подойдёт, но для постоянной работы лучше LTS-версия 21 или 25) и **Node.js 22**. Глобальный Maven не нужен: `mvnw` скачает Maven 3.9.11 сам.

### Вариант 1: без базы (H2 в памяти)

Самый быстрый вариант, данные живут до перезапуска backend.

Backend — в IDEA запустите `MedicalApplication` с профилем `local` (Run Configuration → Active profiles: `local`), либо из терминала:

```powershell
.\mvnw.cmd -pl backend/app spring-boot:run "-Dspring-boot.run.profiles=local"
```

```bash
./mvnw -pl backend/app spring-boot:run -Dspring-boot.run.profiles=local
```

Frontend — во втором терминале:

```bash
npm install
npm run dev -- --port 43127
```

| Что | Адрес |
|---|---|
| Интерфейс | http://127.0.0.1:43127 |
| API | http://127.0.0.1:8081/api/v1 |
| Swagger UI | http://127.0.0.1:8081/swagger-ui.html |
| Health | http://127.0.0.1:8081/actuator/health |

`npm run dev` проксирует `/api` на `http://127.0.0.1:8081` (адрес можно сменить переменной `VITE_API_PROXY`), поэтому cookie сессии и CSRF работают так же, как за nginx. Вход — `admin` / `admin`; остальных сотрудников заведите в разделе «Сотрудники». Если API недоступен, на странице входа доступна песочница по ролям.

### Вариант 2: с PostgreSQL в Docker

Та же база, что и в полном запуске, а backend и frontend — из IDE.

```bash
./scripts/init-env.sh              # один раз, если .env ещё нет
docker compose up -d postgres
```

В Run Configuration для `MedicalApplication` задайте переменные окружения (значения — из `.env`):

```
DATABASE_PASSWORD=<POSTGRES_PASSWORD из .env>
CLINIC_DEV_KMS_KEY=<CLINIC_KMS_KEY из .env>
```

Или из bash:

```bash
set -a; source .env; set +a
```

## Возможности и API

Роли (раздел C [целевой архитектуры](docs/target-architecture.md#c-матрица-rbac)): «Владелец клиники» `OWNER`, «Старший администратор» `SENIOR_ADMINISTRATOR`, «Администратор» `ADMINISTRATOR`, «Менеджер» `MANAGER`, «Врач» `DOCTOR`, «Медперсонал» `NURSE`, «Кассир» `CASHIER`, «Техподдержка» `SUPPORT`. Роль и врач определяются учётной записью, под которой выполнен вход, — переключателей в шапке нет. Все маршруты, кроме входа и служебных endpoint-ов, требуют сессии (`401 UNAUTHORIZED` без неё).

**Навигация.** Сверху — вкладки сервисов: **Дашборды** (Сегодня, Моё пространство, Аналитика, Мои условия работы), **Управление** (Сотрудники, Ставки и условия, Журнал аудита, Экстренные доступы, Внешние выводы), **База данных пациентов** (Расписание, Пациенты, Регистратура, Подписанные документы; График врачей), **Склад** (Остатки, Номенклатура, Накладные; Маркировка, Нормы расхода), **Финансы** (Касса, Продажи и выручка, Услуги и цены), **Диск** (Мой диск, Доступные мне, Корзина). Разделы выбранного сервиса — в боковом меню; сотрудник видит только вкладки и разделы, на которые у роли есть права. Вкладка возвращает на последний открытый раздел сервиса. Тема, данные учётной записи и смена пароля находятся в «Настройках» внизу бокового меню.

**Права.** Роль — набор разрешений вида `<сервис>.<ресурс>.<действие>` (`finance.invoice.write`, `clinical.note.write`); набор зашит в коде (`platform/RolePermissions.java`, версия — `permissionsVersion` в `/auth/me`) и в интерфейсе не редактируется. Сервис проверяет разрешение (`requirePermission`) и затем атрибуты: своя клиника, своя запись, связь с лечением. Клинический текст (заметки, диагнозы, документы приёма) — только у врача со связью с лечением, у владельца и администраторов его нет. Матрица проверяется тестом `RbacMatrixTest` по файлу `backend/app/src/test/resources/rbac-matrix.csv` (роль, метод, путь, ожидаемый статус). Ниже «администраторы» — `OWNER`, `SENIOR_ADMINISTRATOR` и `ADMINISTRATOR`; назначать роли можно не выше своих: владельца и старшего администратора — только владелец, администратора и техподдержку — администраторы.

**«Сегодня»** — домашняя страница всех ролей, кроме врача: врач начинает с расписания, и его персональный дашборд стоит над расписанием. Сверху — **персональный дашборд** (`GET /api/v1/me/dashboard`): виджеты по разрешениям роли, только числа и агрегаты — приёмы за календарный месяц (у врача — свои), приёмы сегодня, неподписанные документы (врач), счета к оплате и ждущие суммы, выручка за месяц, задачи на сегодня, нехватка и истекающие партии на складе, очередь маркировки, ошибки доставки, повторы событий и квота диска. «Сегодня» — первый раздел вкладки «Дашборды»; название AlphaCRM в меню — кнопка «На главную» (врача возвращает в расписание, открытые приёмы остаются). В шапке — дата, имя сотрудника и быстрые действия: «Новая запись» (кто записывает), «Новый пациент» (кто регистрирует), «Касса» (кто видит счета). Блоки, каждый — только ролям с доступом к этим данным: записи на сегодня и завтра без отмен и неявок; просроченные задачи; завершённые и не оплаченные приёмы за 90 дней (включая счета свободной цены, ждущие суммы); ошибки доставки.

**«Моё пространство»** — личный раздел в «Дашбордах» для всех ролей. Пользователь создаёт задачи, заметки и записи с собственными типами и статусами, добавляет текст, теги, чек-листы и произвольные поля, задаёт срок и время напоминания, при необходимости связывает запись с пациентом или приёмом. Есть поиск, фильтры, сортировка, список и доска, архив и сохранённые представления. Записи видны только их владельцу в его клинике; клинический текст в этот раздел не переносится. Напоминание отображается в списке, внешних push-уведомлений нет. В песочнице пространство сохраняется в `localStorage` текущего браузера, остальные демо-изменения остаются в памяти вкладки.

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET/POST /api/v1/workspace/items`, `PUT /api/v1/workspace/items/{id}` | все роли, только свои записи | список (`?archived=true` — архив), создание и редактирование личной записи |
| `POST /api/v1/workspace/items/{id}/archive`, `…/restore` | все роли, только свои записи | архивирование и восстановление |
| `GET/POST /api/v1/workspace/views`, `DELETE /api/v1/workspace/views/{id}` | все роли, только свои представления | список, сохранение и удаление представления |

**ИИ-навигатор.** Отдельная кнопка верхней панели открывает раздел по русскому запросу. Точные совпадения ищутся локально без модели; для неоднозначного запроса backend вызывает OpenAI-compatible `chat/completions`. Модель получает только вопрос, текущий id страницы и каталог доступных роли разделов (id, название, описание, ключевые слова), без пациентов и содержимого записей. Ответ ограничен `destinationId` из этого каталога: URL, код и произвольные действия не принимаются. Вопросы и ответы в базе не сохраняются. Отдельных ИИ-тарифов, оплаты и месячных лимитов запросов нет.

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/assistant/status` | все роли | доступность модели |
| `POST /api/v1/assistant/navigate` | все роли | `{query, currentPage, destinations}` → разрешённый `destinationId` |

**Ошибки.** Ответ с ошибкой — `{timestamp, status, code, message[, fields]}`. `code` — машинный код на английском (`SLOT_ALREADY_BOOKED`, `SERVICE_INACTIVE`, `NO_CARE_RELATIONSHIP`…), `message` — английское пояснение для разработчика. Русскую фразу выбирает интерфейс по коду (`src/api/errorMessages.ts`); если кода там ещё нет, показывается `message` сервера, но не сам код. Неверный логин или пароль — `401 INVALID_CREDENTIALS`, одинаково для обоих случаев.

| Маршрут | Кто | Что делает |
|---|---|---|
| `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`, `POST /api/v1/auth/password`, `GET /api/v1/auth/csrf` | все | вход, выход, текущий сотрудник, смена своего пароля, выдача CSRF-cookie |
| `GET /api/v1/staff` | администраторы, `MANAGER`, `SUPPORT` | сотрудники без хешей паролей |
| `POST /api/v1/staff` | администраторы, `MANAGER` — роли не выше своих | `{fullName, username, password, role, practitionerId, newPractitioner}`. Врачу — либо `practitionerId` карточки своей клиники без учётной записи, либо `newPractitioner: {specialty, room, shifts}`: карточка с тем же ФИО создаётся в той же транзакции (занятый логин или неверная смена — карточки не остаётся), id учётной записи = id карточки. `409 USERNAME_TAKEN`, `PRACTITIONER_REQUIRED`, `PRACTITIONER_TAKEN`, `PRACTITIONER_NOT_ALLOWED`, `PRACTITIONER_AMBIGUOUS` (указаны оба), `INVALID_SHIFT`, `404` для неизвестного или чужого врача |
| `POST /api/v1/staff/{id}/deactivate`, `…/activate` | администраторы, `MANAGER` — роли не выше своих | отключить (себя — `409 CANNOT_DEACTIVATE_SELF`) или включить; сессии отключённого перестают действовать |
| `POST /api/v1/staff/{id}/password` | администраторы, `MANAGER` — роли не выше своих; `SUPPORT` — всем, кроме `OWNER` | новый пароль `{newPassword}`, от 8 символов |

Время во всех запросах — UTC (`2026-10-20T09:00:00Z`); дни недели в рабочих часах — ISO (понедельник = 1).

### Расписание (`scheduling`)

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/practitioners` | все роли | врачи своей клиники: ФИО, специальность, кабинет `room` (может отсутствовать), рабочие часы |
| `GET /api/v1/services[?all=true]` | все роли | справочник услуг своей клиники: название, длительность, цена в копейках, валюта, `active`. Выключенные — только администратору с `all=true` |
| `GET /api/v1/appointments?date=` | все роли; у `SUPPORT` — без `patientId` (маска) | записи за день; фильтры `practitionerId`, `patientId`, `status` |
| `GET /api/v1/appointments?from=&to=` | все роли; у `SUPPORT` — без `patientId` (маска) | записи за период (до трёх лет): история пациента (`patientId`), завершённые приёмы для кассы (`status=COMPLETED`) |
| `POST /api/v1/appointments` | администраторы, `MANAGER`, `NURSE`; `DOCTOR` — только к себе | новая запись; `serviceName` — включённая услуга своей клиники (`409 UNKNOWN_SERVICE`, выключенная — `409 SERVICE_INACTIVE`), на запись сохраняется снимок названия и цены (`serviceName`, `amountMinor`, `currency`) |
| `POST /api/v1/appointments/{id}/reschedule` | администраторы, `MANAGER`, `NURSE`; `DOCTOR` — только свои записи | перенос `{startsAt, endsAt, practitionerId}` из `BOOKED`/`CONFIRMED`, статус не меняется, в outbox ничего не уходит |
| `POST /api/v1/appointments/{id}/status` | администраторы, `MANAGER`, `NURSE`; `DOCTOR` — свои записи | смена статуса |
| `POST /api/v1/appointments/{id}/cancel` | администраторы, `MANAGER`, `NURSE`; `DOCTOR` — только свои записи | отмена активной записи |
| `POST /api/v1/practitioners` | администраторы, `MANAGER` | карточка врача без учётной записи `{fullName, specialty, room, shifts}` (`shifts` — как в `working-hours`, может быть пустым: тогда записать к врачу нельзя). Пустой кабинет хранится как `NULL`, кабинет не уникален. Аудит `PRACTITIONER_CREATED` с именами полей |
| `PUT /api/v1/practitioners/{id}` | администраторы, `MANAGER` | специальность и кабинет `{specialty, room}`; график не трогает. Аудит `PRACTITIONER_UPDATED` с именами изменённых полей (`fields:specialty,room`), без значений |
| `PUT /api/v1/practitioners/{id}/working-hours` | администраторы, `MANAGER` | недельный график целиком `{shifts: [{dayOfWeek, startsAt, endsAt}]}`; дня нет в списке — выходной. `409 INVALID_SHIFT` при повторе дня или конце не позже начала |
| `POST /api/v1/services` | администраторы | новая услуга `{name, durationMinutes, priceMinor, currency: "RUB"}`: название до 255 символов, длительность 1–720 минут, цена в копейках ≥ 0. Сразу доступна в записи. Повтор названия в клинике — `409 SERVICE_NAME_TAKEN` |
| `PUT /api/v1/services/{id}/price` | администраторы | новая цена `{priceMinor}` в копейках. Действует для новых записей; `amountMinor` уже созданных записей не меняется |
| `POST /api/v1/services/{id}/deactivate`, `…/activate` | администраторы | выключить или снова включить услугу. Выключенная не предлагается в новой записи и в листе ожидания, но не удаляется: старые записи хранят свой снимок |

Расписание открывается на сегодняшнем дне (или на дне, выбранном в прошлый раз) и показывается по дням или по неделе (с понедельника): в неделе те же записи и те же действия, что в дне, неделя загружается одним запросом `?from=&to=`. День без смены врача помечен «Выходной», запись на него недоступна. График, цены и справочник услуг ведёт администратор на странице «График и цены»: добавить услугу, сменить цену, выключить или включить. Форма записи берёт список услуг только с сервера; две начальные услуги («Первичный приём», «Повторный приём») — данные миграции, а не массив в коде. Демо-песочница без сервера показывает те же две услуги из `demoServices`.

Правила записи и переноса: интервал целиком внутри смены врача в этот день недели (иначе `409 OUTSIDE_WORKING_HOURS`, форма показывает ту же ошибку до отправки), без пересечений с другими записями врача (`409 SLOT_ALREADY_BOOKED`, дополнительно PostgreSQL exclusion constraint), конец позже начала (`409 INVALID_INTERVAL`), не в прошлом (`409 APPOINTMENT_IN_PAST`, форма тоже не пропускает прошедшее время), услуга из справочника (`409 UNKNOWN_SERVICE`). Смены и день записи — в поясе клиники `CLINIC_TIME_ZONE`.

Статусы: администратор — `BOOKED → CONFIRMED`, `BOOKED/CONFIRMED → ARRIVED | NO_SHOW`; врач, только свои записи — `BOOKED/CONFIRMED/ARRIVED → IN_PROGRESS`, `ARRIVED/IN_PROGRESS → COMPLETED`. Недопустимый переход — `409 INVALID_STATUS_TRANSITION`. Неявка освобождает слот, завершённый приём — нет. При переходе в `COMPLETED` модуль оплаты создаёт один счёт `PENDING` на снимок цены записи.

При создании записи (и при переносе к другому врачу) расписание вызывает `CareRelationshipService.ensureCareRelationship(practitionerId, patientId)`: если активной связи с лечением нет, создаётся новая на год.

### Пациенты (`patients`)

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/patients[?query=]` | все, кроме `SUPPORT`; `DOCTOR` — только со связью с лечением; `CASHIER` — только ФИО | поиск по ФИО, основному и второму телефону без учёта формата номера |
| `POST /api/v1/patients` | администраторы, `MANAGER` | регистрация с первым согласием `{fullName, birthDate, phone, email?, secondPhone?, assignedStaffId?, consentVersion, consentBasis}` |
| `GET /api/v1/patients/{id}` | все, кроме `SUPPORT`; `DOCTOR` — только со связью с лечением; `CASHIER` — только ФИО | карточка |
| `PUT /api/v1/patients/{id}` | администраторы, `MANAGER` | карточка целиком `{fullName, birthDate, phone, email, secondPhone, assignedStaffId}`: пустой или отсутствующий необязательный контакт удаляется. E-mail — простая проверка формата, до 255 символов (`400 VALIDATION_ERROR`). Постоянный администратор — активный `ADMINISTRATOR` своей клиники (`409 INVALID_ASSIGNED_STAFF`, чужой или неизвестный — `404 STAFF_NOT_FOUND`); уже привязанный и потом отключённый остаётся. В аудит — имена изменённых полей (`email,secondPhone,assignedStaff`) без значений |
| `POST /api/v1/patients/{id}/consents` | администраторы, `MANAGER` | новая действующая версия согласия `{version, basis}`; прежние не удаляются |
| `POST /api/v1/patients/{id}/consents/{consentId}/revoke` | администраторы, `MANAGER` | отзыв: ставит `revokedAt`, повторный отзыв — `409 ALREADY_REVOKED` |

| `PUT /api/v1/patients/{id}/registry` | администраторы, `MANAGER` | административные поля `{referralSource, registryNote, telegramChatId, removeTelegram}`: chat id Telegram пациента (только цифры; пусто — не менять, `removeTelegram: true` — отключить; в ответе — только `telegramConnected`, сам chat id сервер не отдаёт никому); откуда пришёл (`RECOMMENDATION`, `WEBSITE`, `INSURANCE`, `DOCTOR_REFERRAL`, `OTHER`, иначе `409 INVALID_REFERRAL_SOURCE`) и заметка регистратуры до 1000 символов |

Согласие «действует», если есть хотя бы одно без `revokedAt`. В аудит — факт и id согласия, без текста основания.

Карточка отдаёт `email`, `secondPhone` и `assignedStaff {id, fullName, active}` (`active: false` — учётная запись отключена) и `phoneSharedWith` — другие карточки, где основной или второй телефон совпадает с любым из телефонов этой (сравниваются цифры, `8…` = `+7…`); e-mail и второй телефон — отдельные контакты `EMAIL` и `SECOND_PHONE`, основной телефон — `PHONE`; интерфейс показывает предупреждение о возможном дубле. Заметка регистратуры в клинический контур не попадает, врачу в интерфейсе не показывается; в аудит пишется только факт изменения и имена полей (`referralSource,registryNote`), без текста.

**Импорт из PostgreSQL.** В разделе «Пациенты» мастер «Импорт PostgreSQL» принимает JDBC URL, логин/пароль источника, таблицу `schema.table`, сопоставление столбцов и лимит до 5000 строк. `POST /api/v1/patients/import/postgresql/preview` показывает `NEW`, `DUPLICATE`, `ERROR`; `POST /api/v1/patients/import/postgresql/commit` создаёт только новые карточки. Дубли определяются по нормализованному телефону и паре ФИО + дата рождения, существующие карточки не перезаписываются, согласия автоматически не создаются. Доступ — `clinical.patient.write`; пароль источника не сохраняется, соединение read-only, имена таблицы и столбцов ограничены простыми SQL-идентификаторами.

**Mango Office.** В карточке пациента кнопка «Позвонить» запускает callback: ВАТС сначала звонит сотруднику на добавочный, затем пациенту. `GET /api/v1/telephony/status`, `POST /api/v1/telephony/calls`, `GET /api/v1/telephony/patients/{id}/calls` доступны сотрудникам с чтением контактов. Mango присылает события на `/api/v1/integrations/mango/events/call` и `/recording`; backend проверяет SHA-256-подпись `vpbx_api_key + json + vpbx_api_salt`, отбрасывает повторы и связывает звонок по телефону только при однозначном совпадении. В базе — журнал и id записи разговора, сама запись не хранится. Настройки — `MANGO_API_KEY`, `MANGO_API_SALT`, `MANGO_DEFAULT_EXTENSION`, при нескольких клиниках также `MANGO_CLINIC_ID`.

### Регистратура (`registry`)

Внутренние задачи сотрудникам и лист ожидания. Это не отправка SMS: пациенту ничего не уходит, outbox не используется.

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/registry/tasks?dueTo=` | администраторы, `MANAGER`, `CASHIER` | открытые задачи клиники со сроком до даты включительно — список «на сегодня», с пациентом и без |
| `GET /api/v1/registry/tasks?patientId=` | те же | все задачи пациента — в карточке; задачи без пациента сюда не попадают |
| `POST /api/v1/registry/tasks` | администраторы | `{title, dueDate, assigneeId, patientId?}`: `title` — свободный текст до 200 символов, исполнитель — активный сотрудник своей клиники (`409 INVALID_ASSIGNEE`), пациент необязателен (`404 PATIENT_NOT_FOUND` для чужого или неизвестного) |
| `POST /api/v1/registry/tasks/{id}/done`, `…/reopen` | исполнитель или администраторы | статус `OPEN` ↔ `DONE` |
| `GET /api/v1/registry/waitlist[?practitionerId=&date=]` | администраторы, `MANAGER` | активный лист ожидания; с фильтром — кто подходит под свободный слот |
| `POST /api/v1/registry/waitlist` | администраторы | `{patientId, practitionerId, serviceId, wishFrom, wishTo}` |
| `POST /api/v1/registry/waitlist/{id}/book` | администраторы | закрыть ожидание ссылкой `{appointmentId}` на запись, уже созданную обычным `POST /appointments` |
| `POST /api/v1/registry/waitlist/{id}/cancel` | администраторы | убрать из листа |

Задача — текст администратора, а не выбор из списка. Задачи, созданные до этого, сохранились: прежние виды стали названием («Перезвонить», «Обновить согласие»). В аудит пишется только `with-patient` или `without-patient`, без текста задачи.

Когда запись отменили или отметили неявку, у слота в расписании появляется кнопка «Ждут: N» с подходящими ожидающими (тот же врач, день внутри желаемого периода). «Записать» создаёт обычную запись — с проверкой смены и пересечений — и закрывает ожидание.

### Клинический контур (`clinical`)

Доступ к тексту — только врачу с активной `care_relationship`; администратору, менеджеру и кассиру клинический текст недоступен.

**Экстренный доступ владельца** (break-glass, решение K1). В карточке пациента у владельца вместо «данные недоступны» — кнопка «Экстренный доступ»: причина из списка (`PATIENT_COMPLAINT`, `LEGAL_REQUEST`, `DOCTOR_UNAVAILABLE`, `QUALITY_REVIEW`, `OTHER`), пояснение от 10 символов и пароль ещё раз. Доступ — к истории этого пациента, только чтение, на 60 минут; продление — новый запрос с новой причиной.

| Маршрут | Кто | Что |
|---|---|---|
| `POST /api/v1/patients/{id}/break-glass` | `OWNER` | `{reasonCode, reasonText, password}` → доступ до `expiresAt`; неверный пароль — `409 WRONG_PASSWORD`, пять подряд — `429 TOO_MANY_ATTEMPTS` на 15 минут |
| `GET /api/v1/patients/{id}/break-glass` | `OWNER` | действующий доступ (`active`) |
| `GET /api/v1/clinical/break-glass?from=&to=` | `OWNER`, `SENIOR_ADMINISTRATOR` | журнал экстренных доступов с причиной и пояснением (раздел «Экстренные доступы») |

С доступом `GET /clinical/patients/{id}/encounters` отдаёт историю владельцу; в журнал — `CLINICAL_BREAK_GLASS_GRANTED` (основание — код причины) и каждое `CLINICAL_HISTORY_READ` с основанием `break-glass`. Текст пояснения хранится зашифрованным в `break_glass_grant` и в аудит не попадает. Старший администратор и лечащие врачи пациента видят на дашборде счётчик экстренных доступов за 7 дней. Писать заметки и подписывать владелец не может.

| Маршрут | Что делает |
|---|---|
| `POST /api/v1/clinical/encounters` | начать приём по записи `{appointmentId, patientId, practitionerId}`. Запись должна существовать, пациент и врач — совпадать с ней, врач — тем, кто вошёл. Начать можно по любой своей записи, кроме отменённой, неявки и завершённой (`409 APPOINTMENT_NOT_STARTABLE`); из «Ожидает», «Подтверждён» или «Прибыл» запись переходит в `IN_PROGRESS`. Несколько записей врача могут быть в `IN_PROGRESS` одновременно. `201` — новый приём, `200` — уже начатый по этой записи (тот же encounter) |
| `GET /api/v1/clinical/patients/{patientId}/encounters` | история приёмов: `appointmentId`, `startedAt`, текст заметки и список версий документа (`id`, `state`, `templateVersion`, `signedAt`, `amendsDocumentId`) — без snapshot и текста документа |
| `PUT /api/v1/clinical/encounters/{id}/note` | черновик заметки: жалобы, психический статус, диагноз, рекомендации |
| `POST /api/v1/clinical/encounters/{id}/documents` | черновик документа `{templateVersion}` из текущей заметки (`409 NOTE_REQUIRED`, если заметки нет) |
| `POST /api/v1/clinical/documents/{id}/sign` | подпись: черновик приводится к текущей заметке, считается хеш, версия блокируется (`SIGNED_LOCKED`) |
| `POST /api/v1/clinical/documents/{id}/amendments` | дополнение к подписанному документу — новый черновик со ссылкой на исходный; исходник остаётся заблокированным |

Клинический модуль не зависит от расписания: данные записи и перевод её в `IN_PROGRESS` он получает через свой порт `VisitAppointments`, который реализует `scheduling`.

Несколько приёмов подряд: кнопка «Начать приём» есть у каждой своей записи дня, кроме отменённых, неявок и завершённых, и не прячется, пока открыт другой приём. Открытые приёмы перечислены в меню слева; переход к другому пациенту не закрывает и не подписывает предыдущий. «Завершить приём» на странице визита ставит записи `COMPLETED` — в расписании сразу «Завершён», и кнопки старта у этой строки больше нет.

**Подписанные документы** (страница для `DOCTOR` и `MANAGER`; администратору и кассиру — `403`, пункта меню нет):

| Маршрут | Что делает |
|---|---|
| `GET /api/v1/clinical/signed-documents[?practitionerId=]` | только `SIGNED_LOCKED`, включая подписанные дополнения; черновиков нет. Врач видит документы, которые подписал сам; менеджер — все документы клиники, фильтр по врачу |
| `GET /api/v1/clinical/signed-documents/{id}` | карточка: пациент, врач, время подписи, шаблон, ссылка на исходный документ для дополнения, жалобы, психический статус, диагноз, рекомендации |

Текст берётся из подписанного снимка документа, а не из текущей заметки. Связь с лечением для архива не требуется: доступ даёт роль и факт подписи. Только чтение: подписать или изменить отсюда ничего нельзя. Чтение пишется в аудит (`SIGNED_DOCUMENT_READ`, основание `list` или `card`) без текста документа. В аналитику и кассу эти данные не попадают.

**Документы PDF пациента** (блок на карточке; кассиру — `403`):

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/patients/{patientId}/files` | администраторы, `DOCTOR` со связью с лечением, `MANAGER` (только подписанные) | имя, размер, состояние, кто загрузил, кто и когда подписал; без байтов |
| `POST /api/v1/patients/{patientId}/files` | администраторы, `DOCTOR` со связью | multipart `file` (+ необязательный `appointmentId` записи этого пациента): только PDF (начинается с `%PDF-`, иначе `409 NOT_A_PDF`), до 10 МБ (`413 FILE_TOO_LARGE`), путь из имени отбрасывается. Состояние `DRAFT` |
| `POST /api/v1/patient-files/{id}/sign` | администраторы — любой файл клиники, `DOCTOR` — со связью | `SIGNED_LOCKED`: SHA-256 открытых байтов, кто и когда подписал. Повторно — `409 ALREADY_SIGNED` |
| `GET /api/v1/patient-files/{id}/content` | черновик — администраторы и `DOCTOR` со связью; подписанный — ещё `MANAGER` и подписавший врач | расшифрованные байты, `Content-Disposition: attachment`; менеджеру черновик — `403 FILE_NOT_SIGNED` |
| `GET /api/v1/patient-files/{id}/inline` | те же, что у `content` | те же байты с `Content-Disposition: inline` — для кнопки «Печать»: интерфейс открывает файл в новой вкладке встроенным просмотрщиком браузера с сессией сотрудника и вызывает печать. nginx отдаёт этот маршрут со своей узкой CSP (`object-src 'self'`), иначе просмотрщик PDF не открывается |
| `GET /api/v1/patient-files/signed` | `DOCTOR` — подписанные им, `MANAGER` — все клиники | список подписанных PDF для архива «Подписанные документы» |

Где загружать: в карточке пациента — блок «Документы PDF» со всеми файлами; на странице приёма — блок «Заключения и файлы приёма»: файл сразу привязывается к этой записи (`appointmentId`), там же «Подписать», «Печать» и «Скачать». «Печать» есть и в архиве подписанных PDF.

Файл шифруется тем же AES-GCM и ключом `KmsPort`, что и заметки приёма; в `patient_file.ciphertext` нет открытых байтов. После подписи байты, имя, хеш и подписант не меняются: отказ в коде и триггер `patient_file_immutable` в PostgreSQL. Замена — новый файл, удаления нет. Без связи с лечением врач получает тот же `403 NO_CARE_RELATIONSHIP`, что при чтении клинических данных. В аудит — `PDF_UPLOADED`, `PDF_SIGNED`, `PDF_READ` только с id файла. Предел PDF пациента — 10 МБ (проверяет сервис); multipart принимает до 100 МБ ради диска, nginx пропускает в `/api/` до 101 МБ.

### Касса (`billing`)

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/billing/charges` | администраторы, `CASHIER`; `MANAGER` — чтение | счета с оплатой: `appointmentId`, сумма, статус, `paymentStatus` |
| `POST /api/v1/billing/charges` | администраторы, `CASHIER` | счёт по приёму, если его ещё нет (`409 CHARGE_ALREADY_EXISTS`) |
| `POST /api/v1/billing/charges/{id}/payments` | администраторы, `CASHIER` | ручная отметка внешней оплаты `{idempotencyKey}`; повтор с тем же ключом не проводится дважды; счёт без суммы — `409 AMOUNT_REQUIRED` |
| `POST /api/v1/billing/charges/{id}/terminal-payments` | администраторы, `CASHIER` | команда терминалу `{idempotencyKey, method: CARD|SBP}` → `202` и `paymentStatus: PENDING`; без адаптера — `409 TERMINAL_NOT_CONFIGURED` |
| `POST /api/v1/integrations/terminal/events` | адаптер терминала, HMAC | результат `{eventId, paymentRef, status, failureReason?}`: `PENDING`, `SUCCEEDED`, `CANCELLED`, `FAILED`, `TIMEOUT`; повтор `eventId` безопасен |
| `POST /api/v1/billing/charges/{id}/void` | администраторы | аннулировать неоплаченный счёт `{reason}` — `DUPLICATE`, `ERROR`, `PATIENT_DECLINED`, `OTHER` → `VOIDED`; оплаченный — `409 CHARGE_PAID` (закрывается возвратом); оплата аннулированного — `409 CHARGE_VOIDED` |
| `POST /api/v1/billing/payments/{id}/refunds` | администраторы | полный возврат `{idempotencyKey, reason}` — `PATIENT_REQUEST`, `SERVICE_NOT_PROVIDED`, `ERROR`, `OTHER` → счёт `REFUNDED`, чек возврата в outbox (`refund-receipt`, порт кассы); повтор с тем же ключом — тот же возврат, второй возврат — `409 ALREADY_REFUNDED` |
| `GET /api/v1/finance/sales?from=&to=&groupBy=` | администраторы, `MANAGER` (агрегаты) | продажи: оплаты по дате оплаты минус возвраты по дате возврата; `groupBy` — `day`, `service` или `practitioner`; без пациентов. Период — до года |
| `PUT /api/v1/billing/charges/{id}/amount` | администраторы, `CASHIER` | сумма свободной цены `{amountMinor}` в пределах услуги (`409 AMOUNT_OUT_OF_RANGE`); счёт `AWAITING_AMOUNT` → `PENDING` |

**Свободная цена** (сценарий D5). Услуга с `priceMode: OPEN` не имеет цены, только пределы `minMinor`–`maxMinor`. При записи суммы нет (можно указать оценку `estimateMinor` в пределах — иначе `409 ESTIMATE_OUT_OF_RANGE`). Завершение приёма публикует событие `AppointmentCompleted`, и касса создаёт счёт `AWAITING_AMOUNT` со снимком пределов; сумму вводят кассир или администратор, после этого счёт оплачивается как обычный. В выручке дашборда — фактическая сумма.

Касса показывает кнопки «Аннулировать» (неоплаченный счёт) и «Возврат» (оплаченный) — с причиной из списка. Раздел **«Продажи и выручка»** во вкладке «Финансы»: период (этот месяц, прошлый, 7 дней, свой), группировка, итог (выручка, оплачено, возвраты, часть по свободной цене) и таблица с полосой доли. Выручка на дашборде — тоже за вычетом возвратов. События `InvoicePaid`, `InvoiceVoided`, `RefundIssued` пишутся в `domain_event_outbox` (только id и суммы) — для будущих потребителей, например отчётов.

«Отметить внешнюю оплату» — ручное подтверждение сотрудника со статусом `MOCK_NO_PROVIDER`, а не ответ банка. Для карты и QR СБП касса отправляет команду через `TerminalPaymentGateway`: в неё входят id платежа/счёта, сумма, валюта, метод и ключ идемпотентности, но не персональные данные. Счёт остаётся `PENDING`, пока адаптер не пришлёт подписанный `SUCCEEDED`; только тогда счёт становится `PAID`, создаются чек в outbox и одно событие `InvoicePaid`. `CANCELLED`, `FAILED`, `TIMEOUT` оставляют счёт неоплаченным и позволяют повторить операцию новым ключом. Повторный или запоздалый ответ не проводит оплату дважды.

Для webhook задайте `TERMINAL_PROVIDER` и случайный `TERMINAL_WEBHOOK_SECRET` (не короче 32 символов). Адаптер банка подписывает сырой JSON заголовком `X-Terminal-Signature` — lowercase hex HMAC-SHA256. Это внутренний provider-neutral контракт, а не протокол какого-либо банка: для реального приёма денег нужен драйвер конкретного банка/поставщика/модели терминала; без него CRM возвращает `TERMINAL_NOT_CONFIGURED`. Чек уходит в онлайн-кассу только при заданном `CLINIC_CASHBOX_URL`; до этого `fiscalStatus` остаётся `QUEUED`, после передачи — `SENT_TO_CASHBOX`.

Один счёт на приём — уникальный индекс по `appointment_id`. Счёт за завершённый приём создаёт касса из события `AppointmentCompleted` (outbox → inbox, повтор безопасен), а не прямым вызовом из расписания. Экран «Касса» (администраторы, кассир; менеджер — только чтение): завершённые приёмы за 90 дней — пациент, врач, услуга, сумма, статус счёта; без диагнозов и текста приёма. Администраторы и кассир выставляют недостающий счёт, вводят сумму свободной цены и принимают оплату. На экран аналитики деньги не выводятся.

### Аналитика и аудит

- **Аналитика**: `GET /api/v1/analytics/appointments?from=&to=[&practitionerId=]` для администраторов, `MANAGER` и `SUPPORT` — агрегаты «дата × врач × статус» без персональных данных; врачу — только свои приёмы.
- **Журнал аудита**: `GET /api/v1/audit[?result=DENIED&objectType=PATIENT]` для администраторов и `MANAGER`; `SUPPORT` видит журнал без объектов клинического контура (пациенты, согласия, приёмы, документы, PDF) — последние 100 событий; экран читает журнал постранично: `GET /api/v1/audit/page?page=0&size=20[&result=DENIED]` → `{items, page, size, total}`, страница с нуля, `size` 1–100, новые события сверху. Колонка «Основание» — короткий машинный код без клинического текста, телефонов, ФИО, текста заметок и значений полей; интерфейс переводит его на русский (`list:12` → «весь список, 12» и `search:3` → «поиск, найдено 3» — одно событие `PATIENT_LIST_READ` на просмотр списка пациентов, а не по событию на каждого; `card` → «из карточки», `fullName,phone` → «изменены: ФИО, телефон», `BOOKED->CONFIRMED` → «Ожидает → Подтверждён», перенос → «20.10.2026 09:00 → 22.10.2026 10:30», `with-patient` → «по пациенту», `without-patient` → «без пациента», `call-back` → «перезвонить» (старые события), `days:1,4` → «рабочие дни: пн, чт», `role:CASHIER` → «роль: кассир», `self` → «сам сотрудник»). Коды, которые повторяют действие, показываются как «—», неизвестные — как есть.

### Склад (`inventory`) и Честный знак

Номенклатура, склады, документы движения, остатки по партиям и маркировка (раздел G целевой архитектуры). Остаток меняется только проведённым документом: черновик можно править или отменить, проведённый — нет (`409 DOCUMENT_NOT_DRAFT`). Расход идёт по партиям FIFO; не хватает остатка — `409 INSUFFICIENT_STOCK`. Провести расход сверх остатка (`{"allowNegative": true}`) могут только администраторы и только для `CONSUMPTION`.

| Маршрут | Кто | Что |
|---|---|---|
| `GET /api/v1/inventory/categories`, `GET /api/v1/inventory/items`, `GET /api/v1/inventory/warehouses` | все, кроме кассира | категории, номенклатура (`marked`, `rxOnly`, единица, GTIN), склады; основной склад создаётся сам (`clinic.inventory.default-warehouse-name`) |
| `POST`/`PUT` тех же маршрутов | администраторы, `MANAGER`, `NURSE` | завести и изменить; маркируемому товару нужен GTIN (`409 MARKING_REQUIRES_GTIN`) |
| `POST /api/v1/inventory/receipts` | администраторы, `MANAGER`, `NURSE` | **поступление в одно действие**: строки с `itemId` или с названием (`name`, `kind`, `unit`, `gtin`) — позиции, которых нет в номенклатуре, заводятся сами в основную категорию вида (`clinic.inventory.default-category.*`); накладная `RECEIPT` сразу проводится. Есть маркируемые позиции без марок — накладная остаётся черновиком (`posted: false`, `waitingCodes`). Повтор с тем же `idempotencyKey` не создаёт второй приход |
| `GET/POST /api/v1/inventory/documents`, `GET/PUT /api/v1/inventory/documents/{id}` | администраторы, `MANAGER`, `NURSE` | документы: приход `RECEIPT`, расход `CONSUMPTION`, списание `WRITE_OFF`, перемещение `TRANSFER`, возврат поставщику `RETURN_TO_SUPPLIER` |
| `POST /api/v1/inventory/documents/{id}/post`, `POST …/{id}/cancel` | так же | провести (`{allowNegative}`) или отменить черновик |
| `GET /api/v1/inventory/balances` | все, кроме кассира | остатки по товару, складу и партии со сроком годности |
| `POST /api/v1/inventory/marking/scan` | администраторы, `MANAGER`, `NURSE` | разбор скана GS1 DataMatrix: GTIN, серийный номер, партия, срок; код, уже лежащий на складе, — `409 MARKING_CODE_DUPLICATE` при проведении |
| `GET /api/v1/inventory/marking/codes` | все, кроме кассира | коды маркировки и их статус |
| `GET /api/v1/inventory/marking/status`, `GET /api/v1/inventory/marking/operations` | администраторы, `MANAGER`, `NURSE`, `SUPPORT` | очередь операций Честного знака и их статусы |
| `POST /api/v1/inventory/marking/operations/{id}/retry` | администраторы, `MANAGER`, `SUPPORT` | повтор операции |
| `GET/PUT /api/v1/services/{id}/consumption-norms` | читают все с доступом к услугам; меняют администраторы, `MANAGER`, `NURSE` | нормы расхода услуги: товар и количество на приём |

**Поступление в два клика.** На любой странице склада — кнопки «Поступление» и «Загрузить из файла». Окно поступления — таблица строк: название с подсказками из номенклатуры, количество, единица, вид (для новой позиции), партия, срок; строки можно вставить из Excel (Ctrl+V) или загрузить файлом `.xlsx`, `.csv` или текстом с табуляциями — колонки узнаются по заголовкам («Наименование», «Количество», «Ед.», «Партия», «Срок годности», «GTIN»), без заголовков берутся по порядку. «Провести поступление» — и остатки обновлены. Позицию можно завести и отдельно («Номенклатура» → «Новая позиция»); категория необязательна.

**Расход по нормам** (сценарий D7). Завершение приёма (`AppointmentCompleted`) создаёт расход с основного склада по нормам услуги. Немаркируемые позиции проводятся сразу; нехватка приём не блокирует — расход уходит в минус, склад публикует `StockShortage`, и регистратура ставит задачу на сегодня (`clinic.registry.stock-shortage-title`). По маркируемым позициям создаётся черновик: его проводят после сканирования марок. В документе — только id приёма, без пациента и диагноза.

**Честный знак.** Проведение документа с маркированным товаром ставит операцию в очередь `marking_operation`, её отправляет `MarkingRelay`. Без настроенного адаптера (`CLINIC_MARKING_ADAPTER=none`) операции ждут с причиной `MARKING_NOT_CONFIGURED`; `mock` — заглушка, отвечает «принято». Боевая интеграция (УКЭП, API ГИС МТ) в этот инкремент не входит.

### Диск (`drive`)

Корпоративный диск клиники (раздел H): папки и файлы с версиями, права и ссылки. Не путать с PDF пациента — клинические файлы остаются в карточке. Все роли пользуются диском (`drive.file.use`), администраторы и техподдержка ещё и управляют квотой и корзиной всей клиники (`drive.clinic.admin`).

| Маршрут | Что |
|---|---|
| `GET /api/v1/drive/nodes?parentId=` | содержимое папки (корень — без `parentId`), только то, что сотруднику видно |
| `POST /api/v1/drive/folders` | папка `{parentId, name}` |
| `GET /api/v1/drive/nodes/{id}`, `GET /api/v1/drive/shared-with-me` | узел с путём и правами; что открыто сотруднику другими |
| `POST /api/v1/drive/files` (multipart `file`, `parentId`), `POST /api/v1/drive/files/{id}/versions` | загрузка файла; новая версия |
| `GET /api/v1/drive/files/{id}/content[?version=]`, `GET /api/v1/drive/files/{id}/versions` | скачать (всегда вложением) файл или версию; список версий |
| `PUT /api/v1/drive/nodes/{id}` | переименовать, перенести |
| `DELETE /api/v1/drive/nodes/{id}`, `POST /api/v1/drive/nodes/{id}/restore`, `GET /api/v1/drive/trash` | корзина; через 30 дней (`CLINIC_DRIVE_TRASH_DAYS`) — окончательное удаление |
| `GET/POST /api/v1/drive/nodes/{id}/shares`, `DELETE /api/v1/drive/nodes/{id}/shares/{shareId}`, `GET /api/v1/drive/principals` | доступ сотруднику (`USER`), роли (`ROLE`), всей клинике (`CLINIC`) или по ссылке (`LINK`): `VIEW`, `EDIT`, `MANAGE`; наследуется вниз по дереву |
| `GET /api/v1/drive/links/{token}[?node=]`, `GET /api/v1/drive/links/{token}/content` | ссылка — только просмотр, срок до 30 дней, открывается после входа сотрудника этой клиники; в базе — хеш токена |
| `GET /api/v1/drive/quota`, `PUT /api/v1/drive/quota` | занято и квота клиники; менять — `drive.clinic.admin` |

Файл больше `CLINIC_DRIVE_MAX_FILE_BYTES` — `413 DRIVE_FILE_TOO_LARGE`, превышение квоты — `409 DRIVE_QUOTA_EXCEEDED`. Содержимое шифруется тем же ключом, что PDF пациента (`CLINIC_ENCRYPTION_KEY`), и лежит в каталоге `CLINIC_DRIVE_STORAGE_DIR` (в Docker — том `quiet-clinic-drive`; добавьте его в резервное копирование). Действия с диском пишутся в аудит без имён файлов.

### Доменные события

Модули общаются событиями с конвертом `{eventId, type, version, clinicId, occurredAt, payload}` (раздел F): событие пишется в `domain_event_outbox` в той же транзакции, что и изменение, и раздаётся после фиксации; обработчик отмечает `eventId` в `domain_event_inbox`, поэтому повтор не создаёт второй счёт или второе списание. Не раздавшиеся события повторяет `DomainEventScheduler` (`CLINIC_EVENTS_*`). Сейчас: `AppointmentCompleted` → касса (счёт) и склад (списание по нормам); `StockShortage` → регистратура (задача). Без потребителей пока публикуются `InvoicePaid`, `InvoiceVoided`, `RefundIssued` и `RolesChanged`. Количество повторов видно на дашборде администраторов и техподдержки.

## Внешние выводы: сообщения пациентам и чеки

Всё, что уходит из CRM наружу, проходит через одну очередь — таблицу `outbox_message` — и доставщик (`communications.OutboxDispatcher`). Второй очереди нет.

**Что ставится в очередь.** Расписание сообщает о событии, а что и когда отправить, решает модуль `communications`:

| Событие | Сообщения |
|---|---|
| Запись создана | подтверждение сразу; если запись на будущий день — напоминание за 24 часа до приёма |
| Запись отменена | сообщение об отмене; неотправленные подтверждение и напоминание отменяются |
| Запись перенесена | сам перенос в очередь ничего не кладёт. Доставщик видит, что время записи сменилось, отменяет неотправленные подтверждение и напоминание на старое время и ставит новые на новое |
| Неявка | неотправленное напоминание отменяется |
| Оплата отмечена | чек для онлайн-кассы |

**Что лежит в базе.** В строке outbox — только шаблон, id записи или платежа, время записи, ключ идемпотентности, канал, статус и машинный код причины. Ни текста сообщения, ни ФИО, ни телефона, ни chat id, ни жалоб, диагноза, заметки или снимка документа. Текст собирается из записи в момент доставки.

**Что уходит пациенту.** Только нейтральный шаблон (`backend/app/src/main/resources/patient-notices.properties`): подтверждение, напоминание или отмена; поля — название клиники, услуга, врач, дата и время. Например: «Напоминаем о записи в AlphaCRM: Повторный приём, врач Александр Петров, 03.11.2026 в 09:00.» Без действующего согласия пациента не отправляется ничего (статус `SKIPPED`, причина `NO_CONSENT`).

**Куда.** Решает порт `NotificationPort`, не контроллер записи:

1. Задан `CLINIC_OUTBOUND_WEBHOOK_URL` — `POST` на него. Так клиника подключает своего бота или SMS-шлюз, не встраивая их в CRM.
2. Иначе задан `TELEGRAM_BOT_TOKEN` и у пациента есть контакт Telegram — тот же текст уходит в Telegram Bot API (`sendMessage`). Телефона недостаточно: chat id пациент получает, только начав диалог с ботом клиники. Администратор вводит chat id в карточке пациента («Регистратура» → «Изменить» → «Telegram chat id»).
3. Иначе — безопасный mock: в лог пишутся шаблон и пометка, что адрес скрыт; сообщение остаётся `PENDING` с причиной `CHANNEL_NOT_CONFIGURED` и уйдёт, когда канал настроят.

**Тело вебхука** (JSON, UTF-8):

```json
{"idempotencyKey":"appointment-reminder:<appointmentId>:<epoch>","template":"appointment-reminder",
 "appointmentId":"…","clinic":"AlphaCRM","service":"Повторный приём","practitioner":"Александр Петров",
 "startsAt":"2026-11-03T09:00:00Z","date":"2026-11-03","time":"09:00","text":"Напоминаем о записи…",
 "recipient":{"patientId":"…","telegramChatId":"123456789"}}
```

Заголовки: `Idempotency-Key` (тот же, что в теле), `X-AlphaCRM-Timestamp` (секунды Unix), `X-AlphaCRM-Signature: sha256=<hex>` — HMAC-SHA256 секретом `CLINIC_OUTBOUND_WEBHOOK_SECRET` от строки `<timestamp>.<тело>`. Получатель проверяет подпись, отклоняет старые timestamp и не отправляет второй раз сообщение с уже виденным `Idempotency-Key`. Телефон пациента в вебхук не уходит; из адресов — только `telegramChatId`, если он есть.

**Онлайн-касса.** Чек (`FISCALIZATION`) в Telegram и вебхук пациента не уходит: для него отдельный порт `FiscalPort`. При заданном `CLINIC_CASHBOX_URL` — `POST {idempotencyKey, operation: "receipt", paymentId, chargeId, amountMinor, currency, paidAt}` с теми же заголовками подписи (секрет `CLINIC_CASHBOX_SECRET`). Без ФИО, контактов и данных приёма.

**Доставщик.** Каждые 30 секунд берёт `PENDING` и `FAILED`, чьё время пришло: помечает попытку (`SENDING`), отправляет и ставит `SENT`. Сетевая ошибка или ответ 5xx/429 — `FAILED` и повтор через 1, 5, 15 минут, 1 и 6 часов (до 5 попыток); 4xx — `FAILED` без повтора. Повтор уходит с тем же ключом идемпотентности, а `SENT`-сообщение второй раз не берётся. Если процесс остановили посреди отправки, через 10 минут вебхук повторяется с тем же ключом, а Telegram — нет (у Bot API нет ключа идемпотентности, второе сообщение пациенту хуже пропущенного).

**Аудит.** `NOTIFICATION_DELIVERED` и `FISCAL_RECEIPT_SENT` — от имени клиники, объект — id строки outbox, основание — `шаблон:канал` (`appointment-reminder:telegram`). Без текста сообщения и без телефона.

**Экран «Внешние выводы»** (администраторы и техподдержка; врач, медперсонал, кассир и менеджер его не видят): последние 100 строк outbox своей клиники — шаблон, запись (время и короткий id) или платёж, канал, статус с причиной, время создания и попыток. Строку с ошибкой можно отправить повторно: `POST /api/v1/outbox/{id}/retry`. Текста сообщения и контакта на экране нет.

| Маршрут | Кто | Что делает |
|---|---|---|
| `GET /api/v1/outbox[?status=]` | администраторы, `SUPPORT` | последние 100 внешних выводов клиники; `status=FAILED` (или другой статус) — только с ним, неизвестный — `409 INVALID_OUTBOX_STATUS` |

Секреты (`CLINIC_OUTBOUND_WEBHOOK_SECRET`, `TELEGRAM_BOT_TOKEN`, `CLINIC_CASHBOX_SECRET`) — только из окружения (`.env`), не из Git и не из Liquibase. Токен Telegram входит в адрес запроса, поэтому адреса запросов наружу не логируются. В профиле `prod` приложение не стартует, если адрес вебхука или кассы задан, а секрет короче 32 символов.

## Telegram-бот клиники

Бот (отдельный проект ClinicaBot) показывает пациенту врачей и свободное время, записывает на приём и принимает ответ на напоминание. Данные он берёт из CRM через отдельный API, а сообщения пациенту по-прежнему уходят из outbox.

**Как включить.** В `.env`: `TELEGRAM_BOT_TOKEN` (токен от @BotFather), `COMPOSE_PROFILES=bot`, `BOT_SOURCE_DIR` — путь к папке бота (по умолчанию `../ClinicaBot`), `CLINIC_TIME_ZONE` — пояс клиники. `CLINIC_BOT_API_TOKEN` создаёт `scripts/init-env.sh`. Дальше обычный `./scripts/start.sh`: сервис `bot` поднимется вместе со стеком и пойдёт в `backend:8081` по внутренней сети.

**Что видит пациент.** Врачи — карточки, у которых есть хотя бы одна смена. Окна — под одну услугу `CLINIC_BOT_SERVICE` (по умолчанию «Первичный приём»): длина окна равна длительности услуги, начала идут каждые 30 минут от начала смены, на 14 дней вперёд и не раньше чем через 2 часа (`CLINIC_BOT_SLOT_STEP`, `CLINIC_BOT_BOOKING_DAYS`, `CLINIC_BOT_MIN_LEAD`). Занятое время считается так же, как при записи из регистратуры.

**Что происходит в CRM.**

| Действие в боте | В CRM |
|---|---|
| Запись | Ищется карточка с тем же ФИО, датой рождения и телефоном; иначе заводится новая. Карточка получает контакт Telegram (chat id) и, если действующего нет, согласие с основанием `telegram-bot`. Запись создаётся с теми же проверками слота, статус «Ожидает». Подтверждение в outbox сразу закрывается как `SKIPPED` / `SHOWN_IN_BOT` — пациент уже видел ответ бота; напоминание за сутки ставится как обычно |
| «Подтвердить» под напоминанием | «Ожидает» → «Подтверждён» |
| «Отменить запись» под напоминанием | запись отменяется; сообщение об отмене не отправляется — пациент только что видел ответ бота |
| «Связаться с оператором» | задача регистратуры на сегодня исполнителю `CLINIC_BOT_TASK_ASSIGNEE` или первому активному администратору |

В журнале аудита автор этих действий — клиника, основание — «через Telegram-бота». Кнопки под напоминанием (`TELEGRAM_REMINDER_BUTTONS=true`) несут `callback_data` вида `cf:<id записи>:yes|no`; бот подтверждает или отменяет запись, только если она принадлежит пациенту с chat id того, кто нажал кнопку.

**API бота.** Вход — заголовок `X-Bot-Token: <CLINIC_BOT_API_TOKEN>`, без сессии и CSRF; сессия сотрудника здесь не действует, а токен бота — на остальных маршрутах. Пустой токен выключает API (`401 BOT_API_DISABLED`), в `prod` токен короче 32 символов не даёт стартовать. nginx этот путь наружу не отдаёт (`404`). Время — в поясе клиники (`2026-11-03T12:00:00+03:00`).

| Маршрут | Что делает |
|---|---|
| `GET /api/v1/bot/clinic` | название клиники, пояс, услуга онлайн-записи |
| `GET /api/v1/bot/practitioners`, `GET /api/v1/bot/practitioners/{id}` | врачи со сменами: ФИО, специальность, кабинет |
| `GET /api/v1/bot/practitioners/{id}/slots` | свободные окна `[{startsAt, endsAt}]` |
| `GET /api/v1/bot/patients/by-telegram/{chatId}` | самая новая карточка с этим chat id или `404 PATIENT_NOT_FOUND` |
| `POST /api/v1/bot/appointments` | `{telegramChatId, lastName, firstName, patronymic?, birthDate, phone, practitionerId, startsAt, consentVersion}` → `201` запись; занято — `409 SLOT_ALREADY_BOOKED`, вне смены — `409 OUTSIDE_WORKING_HOURS` |
| `GET /api/v1/bot/appointments/{id}?telegramChatId=` | запись этого пациента; чужая — `404 APPOINTMENT_NOT_FOUND` |
| `POST /api/v1/bot/appointments/{id}/confirm`, `…/cancel` | `{telegramChatId}`; повторное подтверждение ничего не меняет, повторная отмена — `409 ALREADY_CANCELLED` |
| `POST /api/v1/bot/operator-requests` | `{telegramChatId, title}` → `201 {id, patientId}` — задача регистратуры |

## Архитектура

Подробно — [docs/architecture.md](docs/architecture.md) (модули, путь запроса, безопасность, frontend, правила языка в коде) и [docs/data-model.md](docs/data-model.md) (все таблицы, связи, ограничения, шифрование, аудит, миграции).

Язык в коде: идентификаторы Java, TypeScript и SQL, ключи конфигурации, сообщения логов и `message` в ответах API — на английском; комментарии могут быть русскими; русский текст на экране живёт только в интерфейсе; ФИО, названия услуг и задач — данные и не переводятся.

- Maven reactor с backend-приложением `backend/app`: Spring Boot 4.1.1, Spring Modulith 2.1.1, JPA, Liquibase, PostgreSQL 18;
- модули: staff (клиники, вход и учётные записи), patients, scheduling (включая аналитику), registry (задачи и лист ожидания), clinical/documents, billing, inventory (склад и Честный знак), drive (корпоративный диск), insights (дашборд), communications/outbox, audit и platform (права ролей, доменные события); границы проверяет `ModularityTest`. `staff` и `registry` не зависят от кода других модулей: существование пациента, врача или сотрудника проверяется запросом к таблице;
- сессии Spring Security с cookie `HttpOnly`/`SameSite=Lax`, bcrypt-хеши паролей, CSRF через cookie `XSRF-TOKEN`;
- запрет пересекающихся записей врача: проверка в приложении плюс PostgreSQL exclusion constraint;
- клинические тексты и snapshot документа шифруются AES-256-GCM через заменяемый `KmsPort`; dev-адаптер берёт ключ из `CLINIC_DEV_KMS_KEY`;
- подписанный документ (`SIGNED_LOCKED`) защищён доменным инвариантом и PostgreSQL trigger; исправление — новый связанный документ;
- права ролей — разрешения `<сервис>.<ресурс>.<действие>` в `platform/RolePermissions`, проверка в сервисах через `requirePermission`; матрицу держит `RbacMatrixTest`;
- модули общаются доменными событиями через transactional outbox и inbox (`domain_event_outbox`, `domain_event_inbox`);
- платежи, уведомления и Честный знак — порты с безопасными mock-адаптерами;
- аудит фиксирует чтения и изменения без клинического текста.

## Решение проблем

**`password authentication failed for user "quiet_clinic"` в логе backend.** В Docker осталась база от прошлых запусков с другим паролем: пароль из `.env` применяется только при создании базы. Если данные не нужны — `docker compose down -v` и снова `start`. Если нужны — впишите в `.env` прежние `POSTGRES_PASSWORD` и `CLINIC_KMS_KEY`.

**Backend не стартует с сообщением про `CLINIC_DEV_KMS_KEY`.** В `.env` нет `CLINIC_KMS_KEY` или он короче 32 символов. Удалите `.env` (только если базы ещё нет) и запустите скрипт заново, либо впишите ключ вручную.

**`Расшифрование не выполнено` при открытии приёма.** Ключ в `.env` не совпадает с тем, которым шифровались данные. Верните прежний `CLINIC_KMS_KEY`.

**Порт 8080 или 55432 занят.** Поменяйте `APP_PORT` или `POSTGRES_PORT` в `.env` и выполните `docker compose up -d`.

**`start.sh` падает с `$'\r': command not found`.** Скрипт получил Windows-переводы строк. В репозитории это исправляет `.gitattributes`; для текущей копии: `sed -i 's/\r$//' scripts/*.sh`.

**Backend не стартует: «Задайте CLINIC_ADMIN_PASSWORD» или «…не короче 12 символов».** В `.env` нет пароля начального администратора или он слабый. Запустите `./scripts/start.sh` / `.\scripts\start.ps1` — скрипт допишет его в `.env` и напечатает — или впишите сами.

**Не получается войти: «Неверный логин или пароль».** В Docker начальный вход — `admin` и пароль из `CLINIC_ADMIN_PASSWORD` в `.env` (он действует, только пока администратор создаётся на пустой базе; после смены пароля — новый). Прежние логины `smirnova`, `petrov` и т. д. удалены миграцией. Если администратор забыл свой пароль, а другого администратора нет, задайте новый bcrypt-хеш прямо в базе (`UPDATE staff_user SET password_hash = '<bcrypt>', must_change_password = true WHERE username = 'admin'`).

**На странице входа «Сервер недоступен» и кнопки «Песочница: …».** Backend недоступен: проверьте `docker compose ps` и `docker compose logs backend`. При разработке — `http://127.0.0.1:8081/actuator/health`.

**Смотреть логи и состояние:**

```bash
docker compose ps -a
docker compose logs --tail 100 backend
docker compose logs --tail 100 postgres
```
